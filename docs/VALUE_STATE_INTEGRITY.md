# Value-state integrity and replay protection

## Server-authoritative value tracking

```text
Incoming current value + idempotency key
        |
        v
security.record_value_event (single database transaction)
        |
        +-- validate active tenant and tenant-owned subject/session
        +-- lock the per-subject/value state row
        +-- return the existing result for a duplicate idempotency key
        +-- derive previous value from stored server state
        +-- persist event and advance state atomically
        |
        v
value-jump detector -> activity_anomalies -> risk engine
```

The ingestion contract intentionally does not accept a client-supplied previous value. The first observed value for a subject/value type establishes a baseline and is not scored as a jump. Subsequent values are compared with stored state. The caller must send a stable, unique idempotency key for each logical event and reuse that key on retries.

## Important integration contract

- `currentValue` must come from a trusted tenant backend, not directly from an untrusted browser/mobile client.
- Idempotency keys should be generated by the caller for a logical operation and remain identical on retries.
- The database serializes updates per `(tenant_id, subject_id, value_type)`.
- Event timestamps are assigned by the API/database path; caller-controlled timestamps should not be used for live velocity detection.
- The baseline event is deliberately not flagged. Existing subjects with established values need an authorized provisioning/import flow before relying on jump detection.
- Threshold detection is only a first layer; velocity, frequency, transaction semantics, reversals, and cross-signal correlation remain separate detector phases.

## Database privileges

`security.record_value_event` is `SECURITY INVOKER`, uses an empty search path, and is executable only by `service_role`. No `SECURITY DEFINER` function is introduced. Internal tables retain RLS and no client-role grants.
